# App architecture

JoPie is a SvelteKit frontend that accesses Supabase directly from the browser. A separate Python 3.12/LangGraph service handles semantic entry through caller-scoped HTTPS Supabase RPC. The repository includes its container, captured public baseline, semantic migrations, and disposable fixtures; it contains no SvelteKit server routes. Receipt image analysis is implemented in the semantic-entry service. Live public-schema metadata and the trigger fix were verified on 2026-10-13; hosted service behavior and the remaining response/type alignment are unverified. See [README.md](../README.md) for setup and [Database and service contracts](database.md) for external contracts.

## Startup and authentication

`src/routes/+layout.ts` skips fetching outside the browser. In the browser it gets the Supabase user, then expense categories and the settings allowlist. Its month comes from the `m` query parameter or the current Taiwan month.

`src/routes/+layout.svelte` initializes stores from load data, loads the initial month through `ensureMonthLoaded`, which merges it into the store so concurrent neighbouring-month loads are retained, loads pending schedules, and renders navigation and the auth modal. On mount it subscribes to auth changes through `src/lib/supabase/auth.ts`. Sign-out clears expense and scheduled stores, invokes cache cleanup, and navigates home.

Google sign-in redirects to the app's origin plus its SvelteKit base path. Database access depends on external RLS policies, not just frontend filters.

## Expense reads and writes

`src/lib/data/expenses.fetcher.ts` owns listing, note search, upsert, deletion, and settlement updates. Queries include the current user's personal rows and non-personal rows, with date, scope, and settled filters. Results are ordered by `ts` and `id` descending, but subsequent-page filtering currently uses only `ts`.

The expense store tracks loaded rows and pagination state. `ExpenseDrawerContent.svelte` writes through the fetcher, then updates the store. Single-row store upserts/deletes patch existing monthly cache entries, including removing an old-month row when its date moves across months. Bulk store upserts do not currently persist monthly cache patches.

Monthly retrieval checks memory, then IndexedDB, then Supabase. Cached months become stale after ten minutes. Store-backed views load months through `src/lib/data/month-loader.ts`. `loadMonthIntoStore` merges a cache hit into the expense store without removing rows and records the month as loaded; a stale hit also starts a background revalidation whose result is applied to the shared store whichever page started it (only sign-out discards it). Server rows (a cache miss or a revalidation) are deduplicated by id (the last one wins) and replace that month in the store, removing rows absent from the server result, except rows upserted or deleted locally while that load was in flight, which keep their local state. The cache is then written from the store's resulting month rows, so a locally deleted row is not cached again. Monthly loads read only the first page of up to 500 rows: when the server reports more, no rows are removed, nothing is cached, the month is not recorded as loaded, and a warning is logged. A failed background revalidation or an incomplete month marks the month as needing revalidation, so the next load fetches from Supabase instead of the cache. `ensureMonthLoaded` skips months already recorded as loaded and shares in-flight requests per account session. Single-row upserts, such as an approved scheduled expense, do not mark a month as loaded. Sign-out (`clearAll`) forgets loaded months and in-flight loads, results of loads started earlier are dropped from both the store and the cache, and the cache clear removes the in-memory layer as well as IndexedDB. Explicit refresh in `forceRefetchMonthlyExpenses` reads fresh 500-row pages, replaces the target month in cache/store (including deletions), and guards account/revision changes. Each month also has a local mutation count (bumped by store upserts and deletes); when it changes while a refresh is in flight, the refresh discards its older snapshot and fetches again (up to three attempts) so a concurrently created expense is not overwritten. These paginated reads are not a database snapshot.

The home page renders a buffered carousel with at most seven consecutive days: three days before and after a window anchor, excluding future dates (four cards when anchored at today). Swipes update the selected date when Embla selects a slide, reusing mounted cards inside the buffer. When moving within one card of an edge, the window shifts around the selected date after the animation settles; cards keyed by date preserve shared DOM nodes. The date input and Today button rebuild and center the buffer immediately, including when interrupting a swipe. Expenses are grouped by Taiwan day once per store update and passed to the visible cards. The page prepares the months in the seven-day buffer around the selected date through `loadMonthIntoStore`, beginning during the swipe animation and tracks loading, success (including empty months), and failure per month for the current account. Failed loads show a retry action. This bookkeeping lasts for the home page instance and only guards the page's own status; store updates, including background revalidation, are kept after the page is left. The layout's initial month and the summary month picker use `ensureMonthLoaded`, so the summary requests a month unless it was already recorded as loaded, even when the store holds some of its rows. The summary groups the selected month's rows (`src/lib/utils/summary.ts`) reactively from the store rows, month, scope, and user. Monthly cache retrieval takes only the first page, up to 500 rows by default (see above).

The summary hides the chart legend and shows a 4px dot at the left of each category row. The chart and dots use the same computed color from `src/lib/utils/category-colors.ts`. `createCategoryColorMap` sorts the full category store by `(sort_order ?? 0, id)`, using UTF-16 id comparisons for ties, and assigns a fixed 12-color hex palette by index. Missing `sort_order` uses the database default of zero. Up to 12 registered categories have distinct colors, independent of monthly amounts, group sorting, scope, and navigation. Zero or negative amounts use `#9ca3af` without removing the category's palette slot.

The custom palette varies hue and lightness: `#2486db`, `#d36f22`, `#289f50`, `#d043ad`, `#a55012`, `#6242ff`, `#ee6363`, `#226d87`, `#4291ff`, `#c70074`, `#e252ff`, `#8a43d0`, in index order. It uses blue/orange, brown, green, coral, rose and violet rather than densely packed green/cyan hues; it is not a standard named palette. All entries, including the two reserved colors, differ pairwise by at least 20° circular HSL hue or 12 lightness percentage points after hex rounding. At most three may lie in the 70°–190° yellow-green/cyan band, with at least 40° hue or 12 lightness points between those pairs; the current palette has one. Tests require at least 3:1 sRGB relative-luminance contrast on white and both Moss Night backgrounds from `src/lib/theme.css`: card `#101b20` and page `#0b1215`. Active/reserved saturation is at least 25 percentage points above inactive gray. Inactive gray itself has only 2.54:1 contrast on white and is excluded from the active-color contrast requirement. These numerical rules do not guarantee recognition of 4px dots or distinguishability with color-vision differences; browser review is still needed and the accessible label supplies text values.

Registered categories beyond the palette capacity cycle with `index % 12`. Unknown ids use an unsigned base-31 UTF-16 hash modulo 12; those fallback colors can collide with registered or other unknown ids. Reserved `uncategorized` uses rose `#d9688e`; an empty id uses deep magenta `#b314b3`. Both are outside the ordered palette, consume no index, and become gray for non-positive totals. Adding or deleting categories, or changing `sort_order`, can shift subsequent indices and change existing colors. A rename alone does not change a color. Colors are stable while the category registry remains unchanged, rather than permanently attached to an id.

Categories are fetched with `select('*').order('sort_order')` by the browser layout and copied into `categoriesStore.items`; the row type exposes optional `sort_order`. `LOAD_DEP_KEYS.categories` registers a SvelteKit invalidation dependency, not a persistent category cache. There is no category IndexedDB cache. The store begins empty; SSR skips loading and signed-out layout loads return no categories. If expense groups exist before categories arrive, they use unknown-id hash colors and id labels, with the two reserved ids handled as above. Once categories arrive, Summary reactively recomputes ordered colors and names, so colors may change once. With no expense groups it shows the existing empty state. The layout normally awaits categories before starting its initial expense load; an existing in-memory category list remains available while navigating.

Summary builds the chart's `aria-label` through `summary-chart-label.ts`, for example `本月各類別花費佔比圖，總計 400：合成餐飲 300（75%）、合成交通 100（25%）`. It includes the same summed total as the chart center and each positive category's amount and percentage, rounded independently to one decimal place. Non-positive categories are omitted from the breakdown; the total still includes their amounts to match the existing chart. Mixed negative totals can therefore produce percentages above 100%. When the total is non-positive, the chart retains its existing no-data state. This label provides the total to screen readers because SVG descendants under `role="img"` are not read separately.

The summary groups loaded rows by category: personal rows contribute their full amount; household rows contribute the current user's `shares_json` amount. Settlement queries its own rows and calculates balances and transfers locally; it does not query the inherited monthly balance view described in the database notes.

## Semantic entry

`AIEntryDialog.svelte` hosts one `semantic-entry/SemanticEntryContent.svelte` conversation with text and receipt image attachments, without a mode switch. The component validates images, converts HEIC/HEIF with `heic2any`, obtains signed URLs through `semantic-entry.fetcher.ts`, uploads bytes without the session JWT, and submits paths in v3 `analyze`. A single complete result writes directly; image analysis treats each purchased line item on a receipt as one result, so multiple items or any incomplete result return editable drafts. Pure text analysis retains the existing bounded clarification flow and automatic single-expense creation. The UI blocks closing, Escape, and outside interaction during requests; account/revision guards discard stale results.

`DraftBlock.svelte` displays the current drafts inline. Users can continue with text (`revise`), or enter `DraftEditDialog.svelte` to edit through the shared `ExpenseDrawerContent.svelte` draft mode, merge, ungroup, hide, or restore entries. Draft editing stays local. Only visible entries are submitted by 「全部記帳」 (`commit`), enabled when all are complete; the service independently validates values before batch persistence. `revise` never writes expenses. Drafts, conversation history, and attachment previews stay in modal memory.

Before analyze or commit submission, `pending.ts` saves an account-scoped localStorage v2 list `{v:2,items}`. Items contain only `requestId`, `submittedAt`, `kind`, `expiredAt`, and optional analyze `snippet`/`imageCount` or commit `draftCount`. The snippet is the first 12 Unicode code points of user text, a privacy tradeoff visible on shared devices; full text, history, analysis, image paths, draft contents, amounts, and tokens remain outside storage. Legacy UUID-only records migrate to expired `legacy` items. Only unexpired items count toward the limit of three. A status `not_found` expires an item only after ten minutes from submission; failed lookups and clock rollback do not expire it. Definitive results remove their item. Pending results allow new input, while requests and image conversion still lock interaction.

`PendingTray.svelte` renders the pending list as a title-bar badge and popover inside the AI entry dialog header; `SemanticEntryContent.svelte` passes it to `AIEntryDialog.svelte` through a bindable `header` snippet and owns all state. Rows expand in place to query status (`GET /semantic-entry/:requestId`), retry the retained in-memory attempt, or delete. Delete always re-queries first: `completed` applies the result, a failed lookup keeps the item, and `not_found` opens an alert dialog before removal. Lookups run on dialog open, account restore, tray open, row expand, and a 60-second interval; expired rows seen during a tray opening are removed from storage when the tray closes. Escape and outside clicks close only the popover; tray actions are disabled while a request streams. The three-item cap shows a four-second polite status toast without clearing input. An interrupted commit removes the draft block and opens the tray with that item expanded.

Only failures after a received `persisting` event become uncertain, even if a service error says `uncertain:true`. A lost event can misclassify a write; exact same-ID retries rely on service idempotency, while changed input can duplicate an expense. Unchanged failed text requests and commits reuse their ID and reference date; a commit keeps its identity across an intervening revise, failed or successful, until the normalized drafts change or a final result is confirmed. Image analysis after a pre-persisting failure requires selecting images again and uses a new ID. Uncertain retries preserve exact payloads in an in-memory request map through modal close; reload or account change leaves only status lookup. Account-change pruning subscribes to the user store at module level, so it also runs while the dialog is closed. Revise never enters the pending list. New submissions require working recovery storage. `timeouts.ts` gives text/revise/commit 45 seconds and image analyze 95 seconds, using the service deadline plus 15 seconds capped at Cloud Run plus 5 seconds. Service deadline changes must update those constants.

The separate service authenticates through Supabase `HTTPS `/auth/v1/user``, loads trusted settings/categories/member context and the Taiwan date, checks for a completed request, consumes quota only for new attempts, calls the provider once, normalizes, and persists via one SQL RPC. Completed replays skip the model and quota. Raw text and JWTs are not stored in the request ledger or persisted graph state; external payload tracing is disabled. See [semantic service contracts](database.md#semantic-entry-service).

First creation patches the existing expense store/cache. Replay/status recovery refreshes the snapshot month and any currently known row month instead of applying the old snapshot. The browser does not directly write expenses in this flow. Draft commit results use the same store/cache integration.

## Scheduled expenses

The scheduled store retrieves pending rows through `scheduled-cache-first.ts`, using memory/IndexedDB caching and a 24-hour stale threshold. Due items are derived from pending rows and a clock updated every minute.

Mutations use `scheduled-expenses.fetcher.ts`. Approval creates a regular expense, then deletes a one-time schedule or advances a recurring schedule. The store updates regular expenses and the pending schedule cache. Recurrence supports daily, weekly, and monthly rules in `Asia/Taipei`. See [lifecycle details](database.md#scheduled-expenses).

## Styling, static build, and PWA

The app uses Tailwind CSS, DaisyUI, Bits UI, and shadcn-svelte primitives. Svelte stores and Svelte 5 runes both appear in the code.

`svelte.config.js` uses `adapter-static`, outputs to `build/`, sets `404.html` as fallback, and applies `BASE_PATH` outside development. Home, summary, settlement, search, and settings page modules export `prerender = true`. There is no explicit `ssr = false` export; browser-only data loading is guarded in the layout.

`vite.config.ts` configures the JoPie PWA manifest and prompt-based registration behavior. SvelteKit's automatic service-worker registration is disabled so the PWA plugin can manage registration. PWA support and browser caching do not make remote writes available offline.

The Python backend lives in `services/semantic-entry/semantic_entry/`, uses FastAPI/Uvicorn for HTTP and HTTPX for caller-scoped Supabase and provider requests, and locks dependencies in `uv.lock`. Its strict Python validators mirror the browser TypeScript contract; `packages/semantic-entry-contract/tests/python-parity.mjs` compares normalized requests/hashes and validates real synthetic JSON/SSE HTTP outputs. FastAPI registers explicit health, creation, and status routes, followed by a fallback route that preserves the existing CORS preflight and JSON errors for unknown paths or methods. Request bodies are read directly and validated by the portable validators; automatic OpenAPI, Swagger UI, and ReDoc endpoints are disabled. The lifespan owns the shared HTTPX client and closes it on shutdown. No Node runtime or frontend source is included in the Python container.

Gemini analysis uses an optional provider streaming method and `on_analysis` callback through the existing LangGraph `extract` node and handler Queue. The graph retains `ainvoke`, normalization, fixed clarification questions, and persistence branches. The pure text provider envelope contains only `analysis` and `extraction`; analysis stays outside graph state and persisted data. Image/revise extraction uses `draft_provider.py` and `graph_v3.py`, without analysis callbacks; commit validates values without a model call.

The semantic fetcher requests version 3 SSE and validates analysis request IDs, sequential sequence numbers, event order, and a 200-code-point cumulative cap before updating the dialog. Deploy the v3 service before releasing this frontend. The dialog displays user messages on the right and assistant analysis, clarification questions, and results on the left, with one persistent textarea and an icon send button below a scrollable conversation. The same composer accepts the initial description and clarification replies, with accessible labels for each; phase-specific hints and the active character count sit immediately above it. Processing and terminal phases disable the composer. Recovery, retry, edit, and new-operation actions appear in the assistant result bubble. There is no separate form heading or permanent footer disclaimer. It follows streaming updates while the reader is near the bottom. Analysis stays outside the live status region; each clarification round preserves the previous summary in the in-memory conversation while resetting the active summary. Display messages are separate from the bounded request history and are never sent to the service. New operations, closing, account changes, and page lifecycle events discard the display conversation. Status queries clear the active summary.

## Summary monthly trend

`src/lib/components/summary/MonthlyTrend.svelte` sits below the pie and defaults to collapsed, without persisting expansion. A full-width button with the title「近 6 個月開銷」on the left and a downward chevron on the right toggles expansion; its arrow rotates 180° when expanded, with a transform transition disabled for reduced motion. Pressing it again collapses the chart and its summary. Expanding dynamically imports `MonthlyTrendChart.svelte` and LayerChart and reads the monthly balance view through `src/lib/data/monthly-balances.fetcher.ts`. Only six Taiwan months including the current month are plotted, filling missing months with zero. Personal totals add personal and household `owed`; household totals use household `owed`. Selecting a column or using arrow keys announces its month and amount without navigating. The separate switch action updates the summary month and calls the existing `ensureMonthLoaded`; the pie and category accordion continue to use expense rows.

背景重查時保留既有圖表與已選月份，只有帳號或六個月視窗改變才清空；收合會卸載圖表與狀態訊息，但保留已載入資料；再展開時直接顯示圖表，資料過期則在背景重查，已選月份會重設。折線圖只用兩個主題都有定義的主題變數。

`src/lib/cache/monthlyBalances.ts` caches view rows in memory and IndexedDB for ten minutes, keyed by email and window start. Stale data remains visible if revalidation fails, with a retry action; a failed first load shows an error rather than zeros. Storage failures fall back to memory. Store single-row upserts and deletes invalidate all trend windows and cause an expanded chart to requery, including manual edits, semantic-entry results and scheduled approvals. Read-only bulk store merges do not invalidate it. Sign-out clears both layers; revision guards discard requests from before invalidation. Changes from other clients are detected at the next stale revalidation on expansion, not by realtime subscriptions. This view query does not load six months of individual expenses and does not change the month loader.
